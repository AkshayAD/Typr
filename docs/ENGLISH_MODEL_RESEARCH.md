# Local dictation model research

Checked **2026-10-18** against publisher documentation, publisher model cards, Sherpa's own exports/source, and Microsoft documentation. This is a research shortlist, not a measured ranking. No replacement weights were downloaded, no recognition benchmark ran, and no microphone or desktop interaction occurred during this research.

## Recommendation for this laptop

The intended target is an ordinary Windows laptop with a multicore CPU and at least the documented RAM recommendation. Keep the operating profile at **two CPU recognition threads, no GPU recognition, and capture only during dictation**. Leave graphics capacity available for games. Extra RAM does not make concurrent gaming performance free; exact personal machine inventory is excluded from the repository.

Keep the working Nemotron model as the quality baseline. For a small, low-risk English efficiency experiment, benchmark **streaming Zipformer 20M int8** first: its documented quantized model files total roughly 42 MiB and use the existing Sherpa transducer API. Its age and LibriSpeech training make accuracy on conversational Indian English an important question. For a newer quality/efficiency candidate, **Moonshine Small Streaming** is promising, but needs a separate native streaming adapter. For the user's **90% English / 10% Hindi** requirement, **Nemotron 3.5 multilingual int8** is the most directly relevant experiment; it supports Hindi, but remains a 600M model and is not a demonstrated CPU saving. These are engineering priorities, not claims that any model already beats Nemotron on this machine.

## What has actually been measured here

- The existing English Nemotron int8 engine completed the earlier short synthetic streaming replay successfully. That establishes functionality, not accent accuracy, sustained thermal behavior or gaming compatibility.
- Multilingual Whisper Small processed an earlier **5.92-second** synthetic recording in about **8.2 seconds** using two CPU threads. This is a post-recording recovery option, not proof of comfortable live streaming.
- The current Nemotron ONNX files occupy approximately **631 MiB** locally. The application pins `org.k2fsa.sherpa.onnx` **1.13.8** and currently configures `OnlineRecognizer`, a transducer encoder/decoder/joiner, CPU execution and 16 kHz / 80-feature input.

No alternative in the table has been run on this laptop. Peak working set, process CPU time, battery consumption, finalization latency and recognition accuracy therefore remain unmeasured. Disk weights, archive size and process RAM are different quantities.

## C# compatibility checked against 1.13.8

Read-only inspection of the installed managed assembly and the corresponding upstream tag confirmed:

- `OnlineModelConfig.Transducer` and `OnlineStream.AcceptWaveform`, `InputFinished` and `SetOption(string, string)` exist. This supports the proposed small transducer experiments and the documented Nemotron 3.5 language option. Actual alternative model loading remains untested. [Pinned online model config](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/scripts/dotnet/OnlineModelConfig.cs), [pinned stream API](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/scripts/dotnet/OnlineStream.cs).
- The pinned native source contains Parakeet Unified's streaming implementation. Its preprocessing and buffered context requirements need their own model configuration; changing only the model directory in today's Nemotron configuration is insufficient.
- `OfflineMoonshineModelConfig` contains `Preprocessor`, `Encoder`, `UncachedDecoder`, `CachedDecoder` and `MergedDecoder`. Upstream's Moonshine v2 C# example explicitly uses `OfflineRecognizer` with an encoder and merged decoder. That does **not** make the newer streaming models drop-in replacements. [Pinned config](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/scripts/dotnet/OfflineMoonshineModelConfig.cs), [pinned C# example](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/dotnet-examples/non-streaming-moonshine-v2-decode-files/Program.cs).
- Moonshine's own C API exposes streaming creation, audio submission and transcription. A native P/Invoke adapter is technically feasible; it needs separate lifecycle, cancellation, UTF-8/buffer ownership and packaging verification. No official C# binding was established. [Moonshine C API](https://moonshine-voice.readthedocs.io/en/stable/api/c-api/).

## Hindi and output polish

English-only models should not be selected on the assumption that a text-polishing model can reconstruct Hindi sounds they missed. Keep raw ASR and formatting quality separate in evaluation. For actual Hindi recognition, test Nemotron 3.5 or the existing retained-audio multilingual Whisper path. Roman Hindi is an output-script preference: recognizing Hindi successfully and transliterating its recognized words are separate steps. No code-switching or Roman-Hindi quality guarantee follows from a language being listed.

## Bounded benchmark for the next user-approved idle window

1. Start with the existing model and **one** smaller candidate, Zipformer 20M int8. Acquire only that candidate's required files, pin the release/checksums and review its license. Keep the current recognizer selectable for rollback. No automatic download, inference or scheduled background run while gaming.
2. Use the same consented local corpus: around 3–5 minutes across 10–15 clips, mostly natural English in the user's accent, names/product terms, numbers, self-corrections, quieter speech and room noise. Include a small Hindi/Hinglish subset with reference transcripts; synthetic English speech is only a transport smoke test.
3. Use CPU execution with two recognition threads. Record one cold load and three warm runs per model. Measure process CPU seconds, wall-clock RTF, first partial delay, stop-to-final delay, peak working set and unwanted words during silence. Keep AI polish off when measuring ASR WER and number/name errors.
4. Stop a candidate that cannot sustain real-time processing or accumulates audio backlog. Compare measured accuracy and finalization time before replacing anything. Test UI cancellation and release of the microphone separately.
5. If the smaller transducer meets the resource target but loses too many words, investigate Moonshine Small Streaming's native adapter. If Hindi recovery is the priority, test Nemotron 3.5 next instead. Add Parakeet Unified only if an English quality comparison remains useful. Do not download and benchmark every large candidate by default.

No universal RAM or CPU percentage promise is justified before this comparison. Leave the GTX 1650 unused for recognition during the CPU experiments; game performance, power and fan impact require their own observation in a later agreed test.

## Microphone quality and hardware impact

WASAPI shared capture is an ordinary Windows audio path that can coexist with other capture clients; it does not reserve the device exclusively. That does not guarantee unchanged audio behavior. [Microsoft audio architecture](https://learn.microsoft.com/en-us/windows/win32/coreaudio/user-mode-audio-components).

With **Bluetooth Classic**, opening the headset microphone makes Windows select HFP instead of A2DP. HFP uses mono voice playback/capture, so a game or music can sound worse while the microphone is open even when the application uses shared mode and never changes Windows' default devices. Closing capture permits the normal profile to return. LE Audio can behave differently, depending on the PC, headset and drivers; its capabilities have not been verified for this laptop. [Microsoft Bluetooth Classic behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-classic-audio), [Microsoft LE Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-low-energy-audio).

The practical default is a **built-in or USB microphone selected inside Typr**, keeping the user's existing Windows playback/default device choices. Open it only for an actual recording and release it promptly on finish/cancel. Standard microphone capture is not a firmware or hardware-tuning operation; there is no evidence here of physical laptop damage from this capture path. CPU recognition can still consume power, raise fan activity and interfere with a busy game, so avoid a blanket “zero impact” or “cannot affect hardware” guarantee.

## Confidence

**High confidence:** published model modes, parameter counts where stated, supported language lists, tagged C# API shapes, release asset sizes, and Windows Bluetooth profile behavior. **Moderate confidence:** proposed integration effort and prioritization inferred from those APIs and architectures. **Unverified:** relative accuracy, memory, energy, laptop latency, sustained load and game impact. No model was changed as part of this research.
